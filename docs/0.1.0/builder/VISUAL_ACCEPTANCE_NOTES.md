### 画面 01 的文字/语义缺陷与限制

1. **P1 — Gate 状态语义矛盾。** 当前需求工程师仍显示 `RUNNING`、60%，清单为 `6/7`，且“客户确认记录”为“待补充”；右上却用绿色“通过整体验收”。这会与“无证据不得 PASS”和未完备 Gate 不可交付的规则混淆。应改为“预检 6/7；Gate 决定：未决 / NOT_READY”，只在独立 Gate 完成后显示 `PASS`；若是上一个阶段已通过，必须标明所适用的阶段、run 和时间。
2. **P1 — 流水线与固定 15 阶段规格不完整对齐。** 截图横向只列出部分角色，左侧也只显示 9 个概括性节点；规格要求固定 15 阶段（含 Intake、Product/CAD、Feasibility、Validation、Project/Sales、Chief Review、Packaging 等）。实现应展示完整计划，或明确“此视图仅显示摘要”；任何“跳过”必须展示规则、理由、影响和 Gate 决定（AC-007）。
3. **P2 — 事件断连信息缺失。** 图中有时间列但没有“最后事件时间 / 连接状态 / after_seq cursor / 重连中”。实现时需满足 AC-008/009，避免 UI 在长时间没有心跳时继续看似运行或变为 100%。
4. **P2 — 示例质量分不能代替 Gate。** `92/100`、绿色勾选和“不得空交付”提示应同步展示 `Gate decision`、delivery_allowed、Rubric/Policy version、evidence count、最近验证时间、问题单链接；仅评分不能通过红线。
5. **P2 — “渲染”文字范围不明确。** 对 XLSX/PDF/图片均显示“渲染”按钮易让用户以为 Worker 可运行 Office 或任意文件。实现只可对安全派生产物预览；不可转换时明确“转换中/不可预览”，不得执行宏、外链或脚本（FR-PREV-001）。
6. **范围限制。** 页面中的所有进度、文件和事件仅是演示；静态图不能验证实时、排序、权限、产物版本或暂停命令。

### 画面 02 的文字/语义缺陷与限制

1. **P1 — “选择专业智能体流水线”容易与固定 15 阶段冲突。** 页面显示若干未勾选角色，而 FR-ORCH-001 要求固定计划。建议改成“交付偏好 / 适用性问卷”，提交后仍创建完整的 15 阶段计划；未适用阶段只能由规则 + 理由 + 影响 + Gate 决定处理，不能仅靠用户取消勾选。
2. **P1 — 预检不一致时启动按钮的行为未说明。** 图中“客户验收标准”显示待确认/不勾选结论，但“开始生成方案”处于视觉上的可操作状态。规格要求安全输入与必填字段才可启动；应明确该项到底是阻塞条件、可选风险确认，还是仅提示，并在服务端给出对应状态与原因。
3. **P2 — credits 文案未明确零扣费。** `Estimated credits 0` 不能替代“v0.1.0 暂不扣费”的产品承诺。开始页和提交成功态应明确估算、余额、未写 `DEBIT` 以及 `BILLING_SKIPPED_V0_1_0` 事件的语义。
4. **P2 — 上传卡缺少安全状态的可见入口。** 文件卡展示名称/大小，但没有服务端 MIME、SHA-256、扫描状态或隔离/拒绝原因。可在详情抽屉显示，且 `PENDING_SCAN`/`REJECTED` 必须使启动不可用（AC-005）。
5. **P2 — 模型标签不是质量保证。** “MiniMax Token Plan”与“预检”不会自然达到 GPT 同等产物。提交页应引导用户看到固定质量链：schema/evidence/确定性校验 → 独立 Gate → 返工 → 升级或 `QUALITY_BLOCKED`，而非暗示所选模型可直接交付。
6. **范围限制。** 模型、计费、上传扫描、任务启动及预检均未连接真实服务；这张图不能证明表单、限制、幂等或零扣费真实生效。

### 画面 03 的文字/语义缺陷与限制

1. **P1 — 中心“文档预览”必须标明安全衍生副本。** 图中既列出 `.docx` 来源又展示文档页面，但没有说明它是否由受控 PDF/HTML 转换而来。实现需在 viewer 显示“安全预览副本 / 转换状态 / 原始文件另行授权下载”，避免承诺 Worker 执行 Office（FR-PREV-001、AC-015）。
2. **P1 — 下载按钮需由可机器验证的交付许可驱动。** “已完成”、`96/100`和一份交付清单不是下载资格本身。下载可用态只能来自 `Chief Review=PASS`、无阻塞、manifest 完整和所有 hash 匹配；否则必须禁用并说明原因（AC-016）。
3. **P2 — 短哈希仅可作视觉摘要。** 右侧 8 位/短 hash 在可追溯性上不足；必须可展开/复制完整 SHA-256、artifact ID、版本、来源 run、policy version 与审计时间（AC-014）。
4. **P2 — 质量评分需保留决策上下文。** 增加 Gate decision、Rubric/Policy 版本、检查时间、evidence count、问题单和 `delivery_allowed`。绿色“通过”只能对应独立 Gate 的实际结论，不能是渲染页的前端判断。
5. **P2 — 交付清单的 `38 文件 · 124 MB` 是示例，不是本版承诺。** 不得将示例数字或任意文件类别当作“121 个成品”合同履行；真实清单由已批准 artifact/manifest 动态生成。
6. **范围限制。** 静态画面无法证明预览隔离、签名 URL TTL、撤权后访问失败、下载审计或跨 tenant 防护。

## 给后续 Builder / Dev Self-Check 的最小落地顺序（PLANNED）

1. 先将状态机、权限、事件 schema、artifact/Gate/manifest 数据契约落为可测试 API，避免把 PNG 文案直接当作事实来源。
2. 在真实事件接口可用后实现命令中心；客户端只渲染服务端事件，不推断完成或 Gate 结论。
3. 实现任务工作室时，将上传扫描、服务端校验、幂等启动和不扣费审计置于开始按钮的后端路径。
4. 实现预览与交付时，把 Preview/Download 设计为鉴权后的派生操作，不将原始 Office、R2 object key 或签名 URL 写进静态 HTML/日志。
5. 把所有 P1 语义项变成明确文案、状态字段和独立测试用例；之后再由独立 QA 依据 AC-001–019 验证。
